# WorkFlow — День 8

Основа — седьмой день. Реализованы SLA по приоритетам, эскалация с причиной, вложения, постоянные уведомления и административная аналитика. Использован раздел восьмого уровня Figma: 20 экранов и состояний.

## Запуск

На этом компьютере откройте `start.cmd`, затем **http://127.0.0.1:3007**. База этого дня — `workflow_day8`.

Для другого компьютера нужны Node.js 24 LTS и PostgreSQL. Создайте базу и `.env` по `.env.example`:

```sh
npm ci
npm run db:init
npm run dev
```

`db:init` применяет исходную схему, новые миграции и seed. Повторный запуск сохраняет заявки, файлы, прочитанные уведомления и настройки SLA. Детали обновления старой базы — в `docs/PRODUCT.md`.

Учебные аккаунты: `operator@workflow.local`, `client@workflow.local`, `agent@workflow.local`, `admin@workflow.local`. Пароль **Practice123!**. Сохранена заявка №1043 «не работает перчик», описание «Учебная проверка оборудования».

## Правила

- SLA настраивается отдельно для Critical/High/Normal/Low — в интерфейсе «Критический/Высокий/Обычный/Низкий». Вводите, например, `15 минут`, `1 час` или `1 час 30 минут`. Число без единицы считается минутами.
- Новая настройка действует для новых заявок и при смене приоритета. Срок считается от создания заявки, а не от момента редактирования приоритета. Уже назначенный срок без смены приоритета сохраняется.
- Operator и Admin могут эскалировать назначенную или находящуюся в работе/ожидании заявку. Причина обязательна на сервере. Исполнитель может продолжить работу с эскалированной заявкой.
- Разрешены PNG, JPG/JPEG и PDF: до 10 МБ каждый, максимум пять файлов на заявку. Сервер проверяет фактический размер и содержимое. Файлы сохраняются в PostgreSQL и скачиваются только при наличии доступа к заявке.
- Уведомления получают автор, назначенный исполнитель и активные Operator/Admin. Доступ к чужим заявкам через уведомление не появляется.
- Проверка приближения SLA выполняется каждые 30 секунд при работающем сервере и при чтении уведомлений. Повторные проверки не создают дубли.

Подробные определения SLA, аналитики, миграций и ограничения учебного хранения файлов — в [docs/PRODUCT.md](docs/PRODUCT.md).

## Что базово нужно знать

Миграция меняет уже существующую базу. Seed добавляет примеры для разработки. Это разные операции: сохранённая заявка не должна исчезать при обновлении схемы.

Ограничения файла в браузере помогают пользователю быстро исправить ошибку. Сервер повторяет проверки, потому что запрос можно отправить напрямую. Блокировка заявки в транзакции не позволяет двум параллельным загрузкам обойти лимит пяти файлов.

Уведомление — отдельная запись с получателем и признаком прочтения. Один ключ события предотвращает повторное сообщение при очередной проверке SLA.

Фильтры и период аналитики хранятся в URL. Заявки, настройки SLA, файлы и уведомления хранятся в PostgreSQL. Pinia продолжает хранить только состояние интерфейса.

Проверки используют production-сервер на 3108, временную SQL-схему и чистый браузерный контекст. Нужны PostgreSQL и Chrome; нестандартный путь задаётся `CHROME_EXECUTABLE`. Таймер уведомлений в тестовом сервере отключён, проверки вызываются явно. Рабочая база не используется тестами.

Результаты команд — в `VERIFICATION.md` и `verification-result.json`. Архитектура — в `docs/ARCHITECTURE.md`. Отчёт PERFORMANCE сохранён как исторический результат шестого дня.
